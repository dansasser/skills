## Graph Development outcome containment

For a governed software-lifecycle mutation, load Graph Development before acting. The user's current request, corrections, approved outcome, non-goals, acceptance contract, and authority bound the current run.

A codebase DLG is durable lifecycle state, not authority to execute every graph node in the current request. Graph Development owns the durable DLG and its runtime and projection mechanics. Do not create a parallel TLG, PLG, DLG, plan, or governance workflow. Execute only the current run projection; ready or invalidated nodes outside it, durable backlog, and unrelated definition drift are not current work.

Graph mutations are allowed, but recording one does not promote its nodes. Record or defer unrelated findings. Promote work only when it maps to an existing approved requirement, current regression, or acceptance gap and remains within the approved outcome; changing that outcome requires the user's explicit authority and the skill's migration or successor-run path.

After bounded graph work, return to the requested critical path. Do not recursively repair graph, specification, or governance state unless it is the requested outcome or a mapped acceptance blocker. DLG backlog and out-of-projection state do not prevent current-run completion; completion follows the approved run outcome contract, not the entire evolving DLG.

For excluded or ordinary non-governed work, do not require Graph Development or create lifecycle artifacts.
